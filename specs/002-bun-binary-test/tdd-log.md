## Draft: bazel-lib request (G12)

Not filed. To be filed on bazel-contrib/bazel-lib by the user, or with the user's approval.

**Title**: Export the copy_directory toolchain type and a documented way to reach its tool

**Body**:

A rule that copies the files of its `data` into its own output tree can copy a single file with
the public `copy_file_action` and the exported `COPY_FILE_TOOLCHAINS`. For a directory
(TreeArtifact) in `data` there is no equivalent public path:

- `copy_file_action` cannot copy a TreeArtifact unless `dir_path` names one file inside it, which
  analysis cannot know (`lib/private/copy_file.bzl`).
- `copy_directory_bin_action(ctx, src, dst, copy_directory_bin, ...)` is public
  (`lib/copy_directory.bzl`), but the caller must supply `copy_directory_bin`. Its docstring says
  the tool is "typically the `@bazel_lib//tools/copy_directory` `go_binary` either built from
  source or provided by a toolchain".
- The copy_directory toolchain exposes the tool only through `ToolchainInfo` fields that are not
  documented (`copy_directory_info.bin`, `default`; `lib/private/copy_directory_toolchain.bzl`),
  and no `COPY_DIRECTORY_TOOLCHAINS` is exported the way `COPY_FILE_TOOLCHAINS` is.
- The resolved-toolchain rule in `lib/private/copy_directory_toolchain.bzl` returns
  `toolchain_info.template_variables`, a field its `ToolchainInfo` does not set.
- Building the tool from source needs rules_go, which bazel-lib's `MODULE.bazel` on the BCR
  declares only as a dev dependency (checked for 3.0.0 and 3.7.2).

Request: export the copy_directory toolchain type (for example as `COPY_DIRECTORY_TOOLCHAINS`,
like `COPY_FILE_TOOLCHAINS`) and document how a rule reaches its tool, for example a documented
`ToolchainInfo` field or a `copy_directory_action(ctx, src, dst)` that resolves the toolchain
itself, as `copy_file_action` does.

Context: rules_bun copies each target's declared files into a per-target tree and, without such
an API, fails analysis for a directory in `data`.

Sources: bazel-contrib/bazel-lib at v3.0.0 and v3.7.2, `lib/copy_directory.bzl`,
`lib/private/copy_directory.bzl`, `lib/private/copy_directory_toolchain.bzl`,
`lib/private/copy_file.bzl`, `MODULE.bazel`.

```

```

- `bazel run --noenable_runfiles //<target>`. Bazel clears `RUNFILES_DIR`,
  `RUNFILES_MANIFEST_FILE` and `RUNFILES_MANIFEST_ONLY` for the binary it runs

  only `MANIFEST` and an empty `_main/`, over `<executable>.runfiles_manifest`.

  (`TestRunnerAction.java`), and `RUNFILES_MANIFEST_FILE`, which `test-setup.sh` exports because
  "test programs should use manifest file to find runfiles". The stub picks `RUNFILES_DIR`, an
  existing but unmaterialized directory. Under `processwrapper-sandbox` the same test passes,
  because the sandbox stages a runfiles tree.

the target; adding `RUNFILES_DIR=<executable>.runfiles` and `RUNFILES_MANIFEST_ONLY=1` fails as
above.

`PREFER_DIRECTORY_SOURCE` is `true` (`linux.rs`, `macos.rs`), and every transformed argument
resolves only through the selected source. The README ("Runfiles discovery") bases that preference
on Linux and macOS materializing the runfiles tree, which `--noenable_runfiles` turns off. macOS has the same code path; I have not run it there.

select the directory only when the first transformed argument exists under it; otherwise select
that tier's manifest, for lookup and for the environment exported to the child, as #59 requires

`$RUNFILES_MANIFEST_FILE` (`bazel test` without a sandbox); a staged tree keeps the directory.

`bazel run` and with `bazel test --spawn_strategy=local` would cover both cases.
